Épico 1 Pipeline de dados e score de regiões stretch
US-01 Backend · Scripts de dados
stretch
Coleta e normalização dos datasets públicos
Goal
Ter um dataset limpo por município que sirva de input para o agente de score. Sem isso o US-02 não tem o que processar.
Como dev do time Ponte,
quero escrever scripts que coletam e normalizam datasets públicos (IDEB, censo escolar, cobertura de telefonia),
para que tenhamos um arquivo estruturado por município pronto para o agente de scoring.
Entra
  • Scripts de coleta das fontes públicas
  • Normalização: um registro por município, nulos explícitos
  • Output: CSV/JSON com código IBGE, UF, IDEB, renda, % cobertura
  • fontes.md com URL e licença de cada fonte
Não entra
  • Nenhuma UI
  • Nenhuma lógica de score
  • Dados pessoais ou de clientes
Critérios de aceite
  • Script roda do zero e produz o arquivo sem erros
  • Todos os municípios têm os campos mínimos ou nulo explícito
  • fontes.md lista todas as origens com URL e licença confirmada
US-02 IBM watsonx — agente
stretch
Configuração do agente de score no watsonx
Goal
Ter um agente no watsonx que receba dados de um município e devolva score + explicação. É a inteligência do dashboard — sem ele o US-03-back não tem o que rodar.
Como dev do time Ponte,
quero configurar e testar um agente no IBM watsonx que receba os campos de um município e retorne score, nível e justificativa,
para que o batch e o dashboard consumam essa saída sem lógica de negócio no front.
Entra
  • Agente no watsonx com prompt estruturado
  • Pesos das variáveis configuráveis no prompt
  • Testes manuais com amostras do US-01
  • Contrato: input município → output { score, nivel, fatores[3] }
Não entra
  • Processamento em batch (US-03-back)
  • Nenhuma UI
  • Nenhuma persistência
Critérios de aceite
  • Retorna schema válido para qualquer município do dataset
  • Alterar pesos no prompt muda o score sem redeploy
  • Contrato documentado com exemplos de input/output
US-03-back Backend
stretch
Job de batch: rodar scoring e persistir resultados
Goal
Processar o dataset completo pelo agente do US-02 e salvar os scores no banco, para que o front consulte resultados sem chamar o watsonx a cada request.
Como dev do time Ponte,
quero implementar um job que percorre o dataset, chama o agente do US-02 por município e persiste os resultados no banco,
para que o dashboard acesse scores pré-calculados via API sem latência de inferência.
Entra
  • Job que itera municípios e chama o agente do US-02
  • Persistência: código IBGE, score, nível, fatores, timestamp
  • Endpoint GET /municipios com filtros por UF e nível
Não entra
  • Nenhuma UI
  • Lógica de scoring (agente do US-02 faz isso)
Critérios de aceite
  • Job processa o dataset completo sem falhas
  • GET /municipios retorna dados com filtros funcionando
  • Re-rodar o job atualiza registros sem duplicar
US-03-front Frontend
stretch
Tela do dashboard com mapa de sensibilidade
Goal
Dar uma interface visual para os dados de score. É a entrega visível do Épico 1 e o que aparece na demo.
Como dev do time Ponte,
quero construir a tela do mapa com municípios coloridos por nível de sensibilidade,
para que a visualização de regiões prioritárias esteja pronta para a demo.
Entra
  • Mapa interativo consumindo GET /municipios
  • Filtros: UF, faixa de score, cobertura de rede
  • Clique no município → painel com os 3 fatores do score
Não entra
  • Nenhuma lógica de backend
  • Autenticação ou controle de acesso
Critérios de aceite
  • Mapa carrega e renderiza todos os municípios sem erro
  • Filtros atualizam o mapa em tempo real
  • Painel lateral exibe fatores corretamente para qualquer município
Épico 2 Campanhas — Backend
US-04 Backend · API
Modelagem e API CRUD de campanhas
Goal
Ter a API que o front (US-06) e o pipeline de RAG (US-05) vão consumir. É a fundação do Épico 2 — todas as outras US de campanha dependem dela.
Como dev do time Ponte,
quero implementar os endpoints de CRUD de campanhas e de upload/remoção de documentos,
para que o front de gestão e o pipeline de RAG tenham uma API estável.
Entra
  • Tabelas: campanhas e documentos
  • POST/GET/PATCH/DELETE /campanhas
  • POST/DELETE /campanhas/:id/documentos
  • Validação: apenas PDF e TXT; tamanho máximo configurável
Não entra
  • Lógica de RAG ou indexação (US-05)
  • Nenhuma UI
Critérios de aceite
  • Endpoints respondem corretamente para casos feliz e de erro (404, 422)
  • Desativar campanha seta status = inativa e bloqueia invocação via telefonia
  • Arquivo salvo no storage com caminho persistido no banco
US-05 IBM watsonx + Backend · Worker
Pipeline de indexação RAG por campanha no watsonx
Goal
Transformar os documentos de uma campanha em um índice RAG isolado no watsonx, para que o agente de voz faça retrieval apenas do conteúdo daquela campanha.
Como dev do time Ponte,
quero implementar o pipeline de chunking, embedding e indexação no watsonx por campanha,
para que o agente daquela campanha responda apenas com o conteúdo correto.
Entra
  • Trigger: upload no US-04 enfileira o documento
  • Chunking com tamanho e overlap configuráveis
  • Embeddings + indexação no watsonx com metadado campanha_id
  • Status: processando → pronto | erro
  • Remoção de documento remove seus chunks do índice
Não entra
  • Nenhuma UI
  • Lógica de resposta do agente (US-08-agent)
Critérios de aceite
  • Upload dispara o pipeline e status atualiza até pronto ou erro
  • Busca no índice de uma campanha não retorna chunks de outra
  • Remover documento remove exatamente seus chunks, sem afetar os demais
Épico 3 Campanhas — Frontend
US-06 Frontend
Interface de gestão de campanhas
Goal
Tornar o fluxo de criar campanha, subir documentos e acompanhar indexação demonstrável sem tocar na API diretamente.
Como dev do time Ponte,
quero construir a tela de gestão de campanhas com criação, upload e controle de status,
para que o fluxo completo de configuração do agente seja demonstrável na apresentação.
Entra
  • Lista de campanhas com status e toggle ativo/inativo
  • Formulário de criação
  • Upload via drag and drop (consome US-04)
  • Indicador de status de indexação por documento (polling ou websocket)
  • Remoção de documento com confirmação
Não entra
  • Nenhuma lógica de backend ou RAG
  • Autenticação ou controle de acesso por perfil
Critérios de aceite
  • Criar campanha e upload de documento funciona de ponta a ponta na demo
  • Status de indexação atualiza sem recarregar a página
  • Toggle ativo/inativo reflete imediatamente na API (US-04)
Épico 4 Telefonia
US-07 Telefonia · URA · Provedor
Configuração do fluxo de chamada e URA
Goal
Ter o número 0800 recebendo chamadas e a URA roteando para a campanha certa antes de qualquer lógica de agente entrar.
Como dev do time Ponte,
quero configurar o fluxo de chamada no provedor com URA que lista campanhas ativas e roteia para o handler correto,
para que a ligação chegue ao agente da campanha antes de qualquer AI ser acionada.
Entra
  • Configuração do número no provedor (Twilio ou equivalente)
  • URA que busca campanhas ativas via GET /campanhas
  • Roteamento: seleção do aluno determina a campanha do handler
  • Fallback: sem campanha ativa → mensagem + encerra
Não entra
  • Nenhuma lógica de STT, AI ou TTS (US-08-handler)
  • Nenhuma UI de configuração
Critérios de aceite
  • Chamada recebida chega na URA sem erro
  • URA apresenta corretamente as campanhas ativas no momento da ligação
  • Fallback reproduz mensagem e encerra sem travar
US-08-agent IBM watsonx — agente
Configuração do agente educacional no watsonx
Goal
Ter o agente educacional configurado no watsonx com RAG, pronto para receber uma pergunta em texto e devolver resposta + score de confiança. O handler (US-08-handler) só chama — não configura.
Como dev do time Ponte,
quero configurar o agente educacional no watsonx com system prompt e RAG apontando para o índice da campanha,
para que o handler invoque esse agente passando apenas a pergunta e o ID da campanha.
Entra
  • Agente com system prompt educacional (linguagem acessível, EF/EM)
  • RAG configurado: busca no índice da campanha recebida como parâmetro
  • Comportamento de baixa confiança: retorna sem_resposta: true
  • Testes manuais com perguntas de múltiplas matérias
  • Contrato: { pergunta, campanha_id } → { resposta, confianca, sem_resposta }
Não entra
  • STT ou TTS (US-08-handler)
  • Persistência de histórico (US-09)
Critérios de aceite
  • Resposta coerente para perguntas dentro do conteúdo indexado
  • sem_resposta: true para perguntas fora do escopo, sem alucinar
  • Contrato documentado e testado com amostras reais
US-08-handler Backend · Webhook
Handler de voz: STT → agente → TTS
Goal
Fechar o ciclo da chamada: receber o áudio, transcrever, consultar o agente do US-08-agent, converter em fala e devolver ao aluno. É o único componente que orquestra os outros dois.
Como dev do time Ponte,
quero implementar o handler que orquestra STT → chamada ao agente watsonx → TTS em resposta a cada turno da ligação,
para que o ciclo de pergunta/resposta funcione dentro de uma ligação de voz comum.
Entra
  • Receber áudio do aluno via webhook do provedor
  • STT: transcrição do áudio para texto
  • Chamada ao agente do US-08-agent com { pergunta, campanha_id }
  • TTS: resposta em áudio enviada ao provedor
  • sem_resposta: true → TTS de fallback orientando buscar o professor
  • Disparo de POST /interacoes ao final de cada turno (US-09)
Não entra
  • Lógica de AI ou RAG (US-08-agent faz isso)
  • Persistência direta (delega ao US-09)
Critérios de aceite
  • Pergunta na ligação gera resposta em áudio em latência aceitável
  • sem_resposta: true resulta no áudio de fallback correto
  • Interação registrada via US-09 ao final de cada turno
Épico 5 Histórico
US-09 Backend · Banco de dados
Persistência anônima das interações
Goal
Salvar cada turno de conversa de forma anônima, para que os dados de uso fiquem disponíveis para análise sem nenhum dado pessoal do aluno.
Como dev do time Ponte,
quero implementar o endpoint e a modelagem que registram cada interação de forma anônima,
para que o histórico de uso fique disponível para análise sem armazenar dados pessoais.
Entra
  • Tabela interacoes: campanha_id, pergunta, resposta, confianca, sem_resposta, timestamp
  • Endpoint POST /interacoes invocado pelo US-08-handler
  • Validação: rejeitar payload com telefone, nome ou CPF
Não entra
  • Nenhuma UI
  • Nenhuma lógica de agregação (US-10)
Critérios de aceite
  • Handler do US-08 registra interação via POST /interacoes
  • Tabela não contém campo de identificação pessoal
  • Payload com PI retorna erro 422
US-10 Backend + Frontend · Analytics
Endpoints de analytics e tela de métricas
Goal
Expor as métricas de uso do agente (dúvidas frequentes, taxa de sem_resposta) para que a demo mostre o ciclo completo de melhoria contínua.
Como dev do time Ponte,
quero implementar os endpoints de agregação do histórico e a tela que exibe essas métricas,
para que a demo mostre análise e melhoria do agente com dados reais de uso.
Entra
  • Endpoint GET /analytics/campanhas/:id: top perguntas, % sem_resposta, volume por dia
  • Dados sempre agregados — sem registros individuais
  • Tela de métricas por campanha consumindo esse endpoint
Não entra
  • Retreino automático de modelo
  • Dados de municípios/regiões (Épico 1 — stretch)
Critérios de aceite
  • Endpoint retorna métricas corretas com base nas interações do US-09
  • Tela exibe dados sem expor registros individuais
  • Funciona na demo com dados reais ou de seed
